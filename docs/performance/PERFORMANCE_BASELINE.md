# خط أساس الأداء

**تاريخ القياس:** 26 أغسطس 2026
**النطاق:** SQLite المحلي، فحوصات startup، وبحث FTS على 1,000 إيصال.
**أداة القياس:** `scripts/profile_audit_performance.py`، والبيانات الخام في [startup_profile.json](startup_profile.json).

> هذه أرقام قياس محلي معزول داخل عملية Python واحدة، وليست SLO أو ضمانًا لبيئة الإنتاج. لا تشمل إنشاء QApplication، رسم Qt، شاشة login، بناء كل الصفحات، زمن الشبكة، أو أداء PostgreSQL.

## بيئة القياس والمنهجية

أنشأ benchmark قاعدة SQLite مؤقتة خارج مسار بيانات المستخدم، شغّل schema/migrations، ثم قاس warm `init_db` وفحوصات diagnostics خمس مرات. بعد ذلك أنشأ مجموعة مضبوطة من **1,000 إيصال** مع فهرس FTS5 وفهرس status، وقاس كل استعلام 20 مرة. أُبقي الاتصال الخارجي معطلًا بالكامل.

| الفئة | قيمة القياس |
|---|---:|
| قاعدة البيانات | SQLite مع WAL وFTS5 |
| حجم البيانات | 1,000 receipt |
| تكرار startup/diagnostics | 5 مرات لكل عملية |
| تكرار الاستعلامات | 20 مرة لكل استعلام |
| الشبكة | معطلة |
| GUI painting/login | خارج القياس |

## النتائج

| العملية | الحد الأدنى ms | الوسيط ms | P95 التقريبي ms | الحد الأقصى ms |
|---|---:|---:|---:|---:|
| `self_repair` | 0.081 | 0.086 | 0.419 | 0.419 |
| `init_db` warm | 1.287 | 1.452 | 1.697 | 1.697 |
| `run_all_checks` | 1.470 | 1.530 | 1.789 | 1.789 |
| `check_integrity` | 0.947 | 0.964 | 1.035 | 1.035 |
| `check_indexes` | 0.286 | 0.304 | 0.341 | 0.341 |
| FTS local search | 0.405 | 0.493 | 0.680 | 0.680 |
| indexed status query | 0.347 | 0.405 | 1.246 | 1.246 |

النتائج تشير إلى أن عمليات SQLite المقاسة على هذه المجموعة المضبوطة أقل من هدف البحث المحلي المعتاد البالغ 100 ms بهامش كبير. لكنها لا تثبت عدم وجود تجمد؛ فالـstartup الفعلي ما زال ينفذ diagnostics وinit/seeding قبل event loop، كما أن benchmark لم يقس زمن Qt أو الأجهزة الضعيفة أو ملفات المرفقات الكبيرة.

## ملاحظات وتحسينات منفذة

كان `sync_pending` متصلًا مباشرة بـQTimer في خيط GUI. نُقل الآن إلى `SyncWorker` يعمل داخل `QThread` مستقل، مع منع التداخل وتحديث status bar عبر signal. هذا يعالج مصدرًا واضحًا لاحتمال حجز event loop دون نقل تهيئة قاعدة البيانات عشوائيًا إلى thread.

لم يُنقل `self_repair` أو `init_db` أو seeding إلى الخلفية لأن ذلك يحتاج قياسًا على Windows وإدارة دقيقة لاتصالات SQLite وlifecycle قبل إظهار شاشة login. نقلها دون هذا الدليل قد يزيد السباقات أو يفتح الواجهة قبل اكتمال schema.

## فجوات القياس

ما زال يلزم قياس startup من تشغيل executable على Windows منخفض المواصفات، من process start حتى أول frame قابل للتفاعل، مع قياس p50/p95 وRSS. كما يلزم benchmark لفتح شاشة قائمة كبيرة، pagination، إنشاء/تعديل manifest من 1,000 عنصر، thumbnails، تصدير PDF/Excel، ومزامنة network بمهلة وانقطاع متعمد. هذه القياسات يجب أن تستخدم بيانات اصطناعية غير حساسة أو fixtures منزوعة الهوية، لا سجلات مرضى حقيقية.

| الهدف المستقبلي | طريقة الإثبات المطلوبة | الحالة |
|---|---|---|
| بحث محلي نموذجي أقل من 100 ms | قياس FTS وfilter على 10k و100k سجل عبر Windows وSQLite | غير مكتمل |
| عدم تجمد الواجهة | watchdog يقيس event-loop latency أثناء search/sync/export | جزئي؛ sync نُقل إلى worker |
| فتح 1,000 عنصر دون تجمد | اختبار UI آلي وقياس أول تفاعل/زمن الرسم | غير مقاس |
| تشغيل متعدد الفروع | PostgreSQL staging مع load test معزول | غير مقاس |
| recovery قابل للإثبات | restore دوري مع checksum وفحص محتوى | checksum محلي منفذ؛ اختبار تشغيلي لاحق |

## إعادة التشغيل

يُعاد تشغيل القياس من جذر المستودع بالأمر التالي:

```bash
PYTHONPATH=. python3 scripts/profile_audit_performance.py
```

ينتج الأمر ملف JSON محليًا داخل `docs/performance/startup_profile.json`. لا يجب تشغيل benchmark فوق مسار بيانات المستخدم، ولا تضمين بياناته أو ملفات قاعدة بياناته في Git أو التقرير.
